# 节点地址自动发现实施计划

状态：待确认，尚未修改程序。

## 目标

新增节点时可以留空服务器地址。Agent 连上面板后，显示自动发现的公网 IPv4 和 IPv6；现有节点在 Agent 更新后也自动更新发现地址。转发和链路使用一个明确的有效地址，不能把两个 IP 拼成一个地址。

## 已确认的现状

- 前端 `vite-frontend/src/pages/node.tsx` 和后端 `NodeDto`、`NodeUpdateDto` 都要求 `serverIp` 非空。
- SQLite `schema.sql` 中 `node.server_ip` 为 `NOT NULL`；现有迁移机制位于 `SQLiteConfig.ensureSchema`。
- Agent 的 WebSocket 握手位于 `go-gost/x/socket/websocket_reporter.go`，目前只发送密钥、版本和协议状态。后端在 `WebSocketInterceptor` 已能取得连接来源 IP，但没有保存。
- `serverIp` 被转发入口、隧道和链路配置使用，见 `ForwardServiceImpl`、`UserServiceImpl`、`TunnelServiceImpl`、`GostUtil`。因此它必须保持单个可用地址。

## 实施顺序

1. 数据模型：增加自动发现的 IPv4、IPv6 字段；保留 `serverIp` 作为供现有业务使用的单个有效地址和首次发现前的回退地址。用现有 SQLite 迁移方式兼容已部署数据库。
2. Agent：连接时上报本机网卡上的公网 IPv6 候选地址，并过滤回环、链路本地、私有和临时地址；IPv4 由面板从已认证 WebSocket 连接的实际来源取得，以覆盖常见 NAT 出口场景。明确多地址时的选择规则。
3. 面板：对新旧节点保存已验证的发现结果；有公网 IPv4 时优先作为有效地址，否则使用公网 IPv6。发现失败时保留已有有效地址；新节点显示“待获取”，不能生成无效的 `:端口` 链接。
4. 前端：新增/编辑节点均允许留空 IP；节点卡片分别显示 IPv4、IPv6 和获取状态。IPv6 用于地址加端口时采用 `[IPv6]:端口` 格式。
5. 联动检查：检查转发入口、隧道和链路在地址未获取时的提示与行为；避免在离线、旧版 Agent 或 NAT 情况下显示虚假的可用地址。
6. 本地验证：使用项目现有 Maven、npm、Go 构建/测试方式验证；在独立测试数据上检查创建空地址节点、首次连接、双栈、仅 IPv6、手动地址、断线重连和旧节点兼容。验证失败立即停止提交。

## 部署顺序

先更新面板后端和前端，再更新节点 Agent。旧 Agent 不上报 IPv6 时页面显示未获取且保留现有地址；升级后的老节点在下次连接时自动更新。每一步本地验证后再提交和推送。部署前检查当前运行配置和现有项目端口，避免影响其他容器。

## 待确认的产品规则

自动发现以公网 IPv4 作为转发和链路的默认地址；若没有公网 IPv4，才使用 IPv6。IPv4 和 IPv6 同时展示。旧节点的已填地址仅在无法发现新地址时保留作回退。
